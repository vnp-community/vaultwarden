---

## Problem Statement

`make_config!` is a ~100-line proc-macro-style declarative macro in `src/config.rs`.
It generates the `Config`, `ConfigBuilder`, `ConfigItems`, and admin UI serialization code.

Pain points:
- **No IDE type-checking** inside macro arms — `rust-analyzer` often fails to resolve fields
- **Hard to onboard** new contributors (non-standard DSL)
- **Cross-cutting concerns are implicit** — secret handling (`Pass`) and admin-UI editability are baked in as positional arguments
- **Hard to add validation** without `generated` hacks

---

## Option 1: Migrate to `serde` + `validator`

Replace `make_config!` with:

```rust
#[derive(Deserialize, Serialize, Validate)]
pub struct Config {
    #[serde(default = "default_domain")]
    #[validate(url)]
    pub domain: String,

    #[serde(skip_serializing)] // Replaces Pass type
    pub admin_token: Option<String>,

    // ...
}
```

### Pros

| Benefit | Notes |
|---------|-------|
| Full IDE support | Field jumps, autocomplete, refactoring tools work |
| Standard semantic | Any Rust developer can read it without learning the DSL |
| `validator` crate | Declarative field validation (`#[validate(url)]`, custom fns) |
| `#[serde(skip_serializing)]` | Replaces `Pass` semantics transparently |
| Env override via `envy` or `figment` | Established crates for env → struct loading |

### Cons

| Concern | Impact | Mitigation |
|---------|--------|-----------|
| **Effort** | ~2–3 weeks engineering time | Phased migration (group by group) |
| **Admin UI generation** | Current `GroupData`/`ElementData` is generated by macro | Re-implement as build script or custom `Serialize` |
| **Hot-reload** | Current `RwLock<Inner>` pattern needs preserving | Keep `Arc<RwLock<Config>>` pattern |
| **ENV_FILE loading** | Currently done in `ConfigBuilder::from_env()` | Move to `figment` or keep `dotenvy` + manual parse |
| **`auto` kind** | Derived values depend on each other | Use custom `Default` impls + post-build derive step |

### `figment` + `validator` stack (recommended)

```toml
[dependencies]
figment = { version = "0.10", features = ["env", "json"] }
validator = { version = "0.18", features = ["derive"] }
```

`figment` natively supports:
- Layered config: JSON file → env vars → defaults
- Type coercion
- Error messages with field names

This replaces `ConfigBuilder::from_env()` + `ConfigBuilder::from_file()` merge logic entirely.

## Compatibility Analysis

### `config.json` format

Current `config.json` uses snake_case field names. `serde` preserves this with `#[serde(rename_all = "snake_case")]` — **100% backward compatible**.

### `Pass` type semantics

Currently, `Pass` is a type alias for `String` with special macro handling:
- Never serialized to `config.json`
- Masked as `***` in the admin UI

Migration path: replace with `#[serde(skip_serializing)]` + custom admin UI `DisplayConfig` wrapper.

### `env_only` marker (SEC-MED-04-A dependency)

The planned `env_only` field marker (TASK-SEC-MED-04-A) becomes a simple `#[serde(skip_deserializing)]` attribute instead — **simpler with serde**.

## Recommendation

**Decision: GO — but defer to Sprint 5+ (after AppState migration complete)**

Conditions:
1. Wait until `CONFIG` global is moved into `AppState` (MED-04-A chain) — migration is easier once it's already injectable
2. Implement SEC-MED-04-A (`env_only` marker) using serde attributes from the start
3. Start with Phase 1 as a proof-of-concept before committing to full migration
4. Use `figment` for layered config loading — eliminates the custom `ConfigBuilder` merge logic

**Do NOT** migrate while `CONFIG` is still a `LazyLock<Config>` global — it would create two competing config loading systems.
